A spec is good when two different developers would build the same product from it.
Sections: Goal · Users (who, what they want) · Features with numbered, testable acceptance criteria ·
User journeys (step by step, e.g. "Sign up → verify email → create first booking → pay (test mode) →
receive confirmation") · Data (main entities and fields) · Roles and permissions · Non-functional
(languages, mobile, performance, privacy/KVKK) · Out of scope · Assumptions.
Write acceptance criteria as observable facts: "Submitting an existing e-mail shows 'This e-mail is
already registered' and creates no user." Avoid vague words: fast, nice, easy, secure (say how).
